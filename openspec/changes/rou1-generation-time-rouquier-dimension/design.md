# Design

## Context

See `proposal.md` for motivation and `specs/triangulated-generation-dimension/spec.md` for the observable proof obligations. Issue #917 is already merged. Its `Dimension.lean` umbrella imports `GenerationTime`, and `scripts/StabilityConditionAudit/Dimension.lean` owns the corresponding audit slice.

The existing `ExtensionClosure` is a generic `ObjectProperty` generated by zero objects, members of its input property, and distinguished extensions. Its source deliberately proves only closure under isomorphisms; it does not assert shift-closure, thickness, or a triangulated-subcategory structure.

## Goals / Non-Goals

**Goals:**

- Add the three ROU1 capabilities at the existing canonical roots and keep every comparison downstream of the presentations it compares.
- Keep implementation scopes small and serial where chunks append to the same umbrella and audit slice.
- Use only the bounded three-round review process for this batch.

**Non-Goals:**

- Do not extend or strengthen the existing `ExtensionClosure` definition or add a competing carrier.
- Do not prove the composition law or Stacks 0FXA from #920, geometric bounds, or semiorthogonal-decomposition bounds.
- Do not import algebraic geometry, stability conditions, or `CompactlyGenerated/` into the new dimension modules.

## Decisions

### Ownership and canonical roots

Rouquier dimension is a new generic structure on an abstract triangulated category, so its file belongs under `CategoryTheory/Triangulated/Dimension/` by the Tier 2 placement rule. `CategoryTheory.Triangulated.rouquierDim` is a scalar invariant; the canonical carrier remains Mathlib's `ObjectProperty`, and the closure operations remain Mathlib's `triangEnvelopeIter`, `triangEnvelope`, and extension products.

Generation-time and image-of-property declarations stay in `CategoryTheory.ObjectProperty`, where the relevant Mathlib API is defined. The Rouquier-dimension consequences stay in `CategoryTheory.Triangulated`. The projection chain is: finite Rouquier dimension gives a single strong generator, which gives a classical generator. No new structure, category, quotient, or typeclass is introduced, so there are no new instance diamonds to reconcile.

### File and import direction

- #918 adds `Dimension/ExtensionClosureComparison.lean`, importing the existing extension closure and generation-time APIs. It compares the two presentations downstream and leaves `ExtensionClosure.lean` unchanged.
- #919 adds `Dimension/Rouquier.lean`, importing generation time. It owns Rouquier dimension and its characterisations, but not equivalence invariance.
- #921 adds `Dimension/Functor.lean`, importing the dimension API it consumes. It owns functor transport and equivalence invariance.
- `Dimension.lean` re-exports those leaves in dependency order. The parent `Triangulated.lean` already imports `Dimension`, so it should need no edit.
- Append declarations to the existing `scripts/StabilityConditionAudit/Dimension.lean`; the audit glob already discovers that slice.

The shared `Dimension.lean` and audit slice mean the implementation order is #918, #919, then #921. The first manifest stacks #918 and #919 to avoid concurrent edits. A successor manifest selects #921 only after #919 is merged; this keeps #921's live blocked status truthful during the first preflight.

### Mathematical boundaries

Use the nonempty and triangulated hypotheses for `ExtensionClosure P ≤ P.triangEnvelope`. The empty-property counterexample rules out weakening the theorem to an unconditional statement. The supremum equality is claimed only if both inclusions are proved; otherwise record the proved inclusions and the exact obstruction.

Rouquier dimension is an infimum over objects, not over arbitrary object properties. It returns a value, not a chosen generator. Keep the `⟨G⟩_{n+1}` convention explicit so the zero-offset and zero-dimensional characterisations cannot drift.

Functor transport is pointwise and in the forward image direction. Do not claim the reverse inclusion for a general functor. If the equivalence proof needs the quasi-inverse to be triangulated, prove that fact or record the exact supplied API in the docstring rather than assuming it.

### Review and recovery protocol

Run the altitude and hypothesis-elimination advisors before freezing file lists, then use the four independent mathematical, repository-boundary, abstraction, and Mathlib reviewers on the same commit for each chunk. Preserve verbatim findings in the controller ledger.

This is a multi-issue batch, so bounded automatic recovery is disabled: recovery manifests currently require one issue and one chunk. If a chunk exhausts its three review rounds, preserve the ledger and stop it. A later recovery attempt needs its own manifest, research evidence, independent review of the exact recovery plan, and inherited findings; recovery does not expand the current scope or provider permissions.

## Risks / Trade-offs

- **Index off by one:** document that Mathlib's zeroth iterate is Rouquier's first envelope and use that convention in every characterisation.
- **Empty generators:** keep `P.Nonempty` on the reverse closure inclusion; the `P = ⊥` counterexample is part of the API documentation.
- **Supremum equality does not close:** retain only proved inclusions and explain the missing argument instead of asserting the desired equality.
- **Quasi-inverse compatibility is missing:** prove the triangulated structure of the quasi-inverse or stop with that exact seam; do not postulate it.
- **Loop preflight currently rejects all three selected issues:** each has the `blocked` label. The text dependency of #918 and #919 is #917, now closed; #921 is blocked by #919 until that issue is completed. Both manifests remain disabled pending user review and explicit enablement. The first preflight will fail until the blocked labels on #918 and #919 are reconciled; the successor preflight must wait until #919 is merged and #921's blocked label is reconciled. Each preflight must run from a clean checkout at the exact base.

## Migration Plan

There is no API migration: changes add declarations and append umbrella/audit imports. First validate this OpenSpec change and both disabled manifests, then have the user review and enable the exact issue/action scope. Reconcile the live `blocked` labels only when their dependencies are satisfied, and run each preflight from a clean worktree at the exact `origin/main` base. Execute #918 then #919; after #919 merges and closes, start the one-issue #921 successor manifest. Build only the changed Lean modules with `LEAN_NUM_THREADS=2 ~/.elan/bin/lake`, run `scripts/precheck.sh` and the focused dimension audit, and require the protected `ci` check on each PR. Never run `scripts/gates.sh` locally or claim local checks are CI.
